# 經驗與血淚史 (Experience)

這份文件記錄了專案開發過程中，那些踩過坑、浪費過無數時間 Debug 所換來的真實教訓。
每一條都採用「四段式結構」，確保未來的我們（與 AI 助手）不會再重蹈覆轍。

## 1. 核心評測邏輯的一致性 (Judger Consistency)

- **理論上 (Theory)**：只要本地端 (Local Judger) 和後端都有實作評測功能，兩邊跑出來的結果理當一樣。
- **實際上 (Actually happened)**：在幾次實際測試下來發現，兩邊對同一份程式碼的評測結果竟然不相同，造成嚴重的成績不一致。
- **解決方案 (Resolved by)**：反覆比對並強制同步兩邊的對比演算法，確保邏輯完全對齊。
- **教訓 (Lesson)**：**前後端的核心功能必須保持絕對一致。** 尤其是像評測這種高敏感度的邏輯，不能只是「規格看起來一樣」，必須保證演算法與處理邊界條件的方式完全相同。

## 2. 環境依賴的提早驗證 (Environment Pre-check)

- **理論上 (Theory)**：程式碼沒問題，換到考場機器上自然就能順利運作。
- **實際上 (Actually happened)**：因為沒有在考試開始前確認環境（例如考試機器沒有設定對應的環境變數），導致學生開始考試時系統直接掛掉。
- **解決方案 (Resolved by)**：在系統啟動或考試開始前，必須加入環境檢查機制。
- **教訓 (Lesson)**：**Fail-fast (提早失敗)。** 絕對不能讓環境缺失的問題在「考試進行中」才引爆，必須在「啟動考試前」進行強制性的環境依賴驗證。

## 3. 子程序的防護與極端輸出 (Child Process & Output Limits)

- **理論上 (Theory)**：當前端 UI 呼叫停止時，底層的評測 Child Process 就會乖乖停下來。
- **實際上 (Actually happened)**：當學生寫出無限迴圈時，前端雖然喊了停止，但後端程序並沒有真正被 kill 掉。更慘的是，當學生程式印出無限多訊息（超出 max output limit）時，過量的資料直接塞爆傳回前端，導致整個前端 UI 嚴重卡頓死機。
- **解決方案 (Resolved by)**：針對 Child Process 實作強制的超時擊殺 (timeout kill) 機制，並對輸出流設定嚴格的緩衝區上限。
- **教訓 (Lesson)**：**永遠不要信任學生的程式碼。** 所有的底層執行緒都必須有「不依賴前端狀態」的硬性 Timeout 保護；且任何跨程序通訊 (IPC) 都必須對傳輸資料量設下嚴格的防禦性上限，以保護主程序不被拖垮。

## 4. 基礎設施的測試流程 (Lack of Standardized Testing)

- **理論上 (Theory)**：功能寫完，開發者自己手動測過幾次沒問題就好。
- **實際上 (Actually happened)**：像 Judger 這種核心基礎設施，在實際面對學生千奇百怪的程式碼時，出現了非常多意想不到的狀況與例外錯誤。
- **解決方案 (Resolved by)**：意識到必須為 Judger 建立一套標準化的測試過程。
- **教訓 (Lesson)**：**核心引擎不能依賴手動測試。** 越底層、越核心的系統（如評測機），必須建立自動化且涵蓋各種極端邊角案例 (Edge cases) 的標準測試流程，否則永遠修不完未知的漏洞。
