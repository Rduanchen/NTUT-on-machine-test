# 桌面版架構與測試策略 (Desktop Architecture & Testing)

## 問題與背景
目前桌面版的評測依賴外部 CLI 指令，容易受學生環境影響（如未設定 PATH）。同時，由於系統採用 Local-First 架構，當助教從後台透過 Piston 重新執行學生的程式碼並覆蓋後端資料時，學生的本地資料與後端會產生不同步。我們需要確保在重新連線或同步時，前端能正確以 Piston 的結果覆寫本地結果，且不產生衝突。此外，桌面版也缺乏自動化測試的防護網。

## 方案與設計 (Designs)

### 1. GCC 編譯器打包 (GCC Bundling)
- **設計**：預先下載對應作業系統的 GCC 執行檔至 `resources/gcc`，並利用 `electron-builder.yml` 的 `extraResources` 進行打包。
- **Why**：與目前的 Python 打包方式一致，呼應 `experience.md` 中的「環境依賴提早驗證」原則，確保桌面版擁有自給自足的評測環境，避免因使用者環境差異導致的突發崩潰。

### 2. 測試策略：UI 元件黑箱測試
- **設計**：沿用現有專案的 Vitest，搭配 Testing Library 進行 Component 等級的黑箱測試。
- **Why**：利用現有的工具鏈，不需要導入龐大的 E2E 測試框架，能在輕量級的環境中驗證 UI 互動與渲染。

### 3. 測試策略：核心邏輯白箱測試
- **設計**：針對核心邏輯（尤其是評測流程與狀態機），利用 `@vitest/coverage-v8` 達成 100% 分支覆蓋率。
- **Why**：這有助於防堵極端邊界條件（Edge cases）導致的桌面版崩潰。

### 4. 測試策略：Local-First 資料覆蓋邏輯
- **設計**：針對處理資料同步與合併的函數（如 Reducer / Action），撰寫**單元測試 (Unit Test)**。
- **Why**：此情境的核心痛點是「資料流與合併邏輯的對錯」——必須確保當前端抓取到後端被 Piston 覆寫的新資料時，能辨識其權重並正確更新本地狀態，而不會反向把本地的舊資料又推回後端。單元測試能以極快的速度與高隔離性，100% 確認這段合併邏輯（Sync / Merge）的正確性。
